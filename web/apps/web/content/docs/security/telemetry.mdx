---
title: Telemetry and network
description: Telemetry is off unless you opt in. This page lists every network connection amicu makes, and exactly what opted-in deployments send.
---

By default amicu sends no telemetry, analytics, crash reports or update checks. There is no account, and `init`, `fmt`, `validate`, `plan`, `apply`, `destroy`, `doctor` and `skill export` do not contact any amicu-operated server. The only HTTP clients in the code are the ones listed below.

If you opt in to telemetry (see [Telemetry setting](#telemetry-setting)), each deployment that `amicu apply` starts on your machine runs a small agent next to it. **The agent makes outbound HTTPS calls to `api.amicu.dev`.** The [Opt-in telemetry](#opt-in-telemetry) section lists exactly what it sends.

## Connections the CLI makes

| When | Destination | What is sent |
|---|---|---|
| `validate`, `fmt`, `init`, `doctor`, `skill export` | None | Nothing. These commands are offline. Provider region and GPU catalogs are compiled in. |
| `plan` | None, unless state records a remote deployment | Offline for local-only projects. If state holds a remote provider deployment, `plan` first asks that provider whether it still exists (today only Modal does this; see the provider rows below). |
| `apply` on this machine | `127.0.0.1:<port>` | Health probes and the endpoint auth check (`GET /v1/models`) to the service amicu just started. If you set an `api_key`, the check sends it as a Bearer header to that loopback address. |
| Provider rows: `apply`, `plan` and provider commands when a remote provider is involved. Today, Modal: | `api.modal.com:443` (gRPC over TLS) | Your Modal token pair for authentication, and the app, image, and function definitions needed to deploy: image build steps, the launch command, GPU and region request, and a Modal Secret holding the endpoint API key (and `HF_TOKEN` if set). `plan`, `apply` and `destroy` also look up whether recorded apps still exist whenever state contains a Modal deployment. |
| Provider rows, RunPod: `apply`, `plan` and `destroy` | `api.runpod.io:443` (HTTPS) | Your `RUNPOD_API_KEY` for authentication, and the endpoint definition: image, launch command, GPU and data center request, and RunPod secrets holding `HF_TOKEN` if set. |
| `apply` on a remote provider (Modal today) | The deployment's Modal URL | The endpoint auth check, and the proxy token headers (`Modal-Key`, `Modal-Secret`). |
| `amicu modal metrics` | The deployment's Modal URL | A `GET /metrics` with the proxy token headers. Hardware metrics use a read-only probe run inside the container through Modal's API. |
| Only when telemetry is on: the telemetry agent next to each local deployment | `127.0.0.1:<port>/metrics` | A `GET /metrics` to the deployment's own server, about once a minute. Nothing leaves the machine. |
| Only when telemetry is on: the telemetry agent | `api.amicu.dev:443` (HTTPS) | About one `POST /v1/telemetry/rollups` per deployment per hour, carrying the [fields listed below](#what-is-sent). |

Credentials are sent only to the endpoint they protect. The exposure check does not use environment HTTP proxies and does not follow redirects, so a key is never forwarded elsewhere.

## Connections that are not amicu's

Amicu starts runtimes that make their own connections:

- **RunPod workers** download model weights from Hugging Face when they start, and pull the same base images. If you set `HF_TOKEN`, it is stored as a RunPod secret and available to the worker.
- **Modal containers** download model weights from Hugging Face when they start, and pull the base container image (by default `vllm/vllm-openai` or `ghcr.io/ggml-org/llama.cpp`). If you set `HF_TOKEN`, it is available to that container.
- **llama-server and vLLM on your machine** are third-party programs. Whatever they fetch (for example a model when given a Hugging Face reference by `extra_args`) is their behavior, not amicu's. Amicu itself does not download model files for local deployments.
- **Clients** you point at the endpoint talk to it directly. Amicu is not in the request path and never sees prompts or completions.

## Telemetry setting

Telemetry is off by default. You can record an opt-in with `amicu telemetry enable`, and undo it with `amicu telemetry disable`. The choice is stored per user, not per project, in `$XDG_CONFIG_HOME/amicu/telemetry.json` (or `~/.config/amicu/telemetry.json`). It is never written to project state.

The effective setting is resolved in this order, strongest first:

1. `DO_NOT_TRACK` set to a true value (for example `1`) forces telemetry off.
2. `AMICU_TELEMETRY=0|1` (also `false`, `true`, `off`, `on`, `no`, `yes`) overrides the stored choice.
3. The stored choice.
4. The default: off.

`amicu telemetry status` shows the effective setting and its source, the choice saved in the file, any `DO_NOT_TRACK` or `AMICU_TELEMETRY` override set in your shell, and how many telemetry agents are installed and running on this machine and how many deployments have buffered data. It warns when telemetry is off but agents are still installed. The telemetry commands make no network calls.

The first interactive `amicu init` or `amicu apply` asks once whether to share anonymous performance metrics. The default answer is No, and a No is stored, so the question is not asked again. The question is not asked when:

- stdin, stdout or stderr is not a terminal,
- `--output json` is set,
- one of `CI`, `GITHUB_ACTIONS`, `GITLAB_CI`, `BUILDKITE`, `CIRCLECI`, `TF_BUILD`, `JENKINS_URL` or `TEAMCITY_VERSION` is set to a non-empty value other than `0` or `false`,
- `AMICU_TELEMETRY` or `DO_NOT_TRACK` is set, or
- a choice is already stored.

If the stored file exists but cannot be read, the question is skipped and the file is left as it is.

## Opt-in telemetry

When the effective setting is on at `amicu apply` time, apply starts a second job next to each launchd (macOS) or systemd (Linux) deployment. The job is `io.amicu.telemetry.<project>.<deployment>`, and it runs `amicu telemetry-agent`. The job holds no secrets. It is stopped before its deployment whenever amicu stops, updates or destroys that deployment. When the setting is off at apply time, no agent is started.

The agent:

- reads the server's own Prometheus `/metrics` on `127.0.0.1` about once a minute. It never proxies or sees a request, so it does not affect request latency. llama-server serves `/metrics` because amicu always starts it with `--metrics`. vLLM serves it by default.
- runs the same read-only hardware probe as `amicu modal metrics` (`nvidia-smi`, `amd-smi`, `xpu-smi` or `ioreg`) to read accelerator utilization and memory.
- adds up each 5-minute window and keeps the result in a queue at `$XDG_DATA_HOME/amicu/telemetry/queue/` (or `~/.local/share/amicu/telemetry/queue/`). Only you can read the queue files (0600). Each deployment's queue holds at most 512 KiB and 7 days of data. When it is full, the oldest entries are dropped first.
- uploads the queue about once an hour, at a random time within each hour. Each request is under 64 KB. A failed upload (the endpoint is down, unreachable, or answers 503) is retried later with exponential backoff. Until then the data waits in the bounded queue. A batch the server rejects as invalid is dropped, not retried.
- reads the saved choice in `telemetry.json` again before every scrape and every upload. If the file says off, it collects nothing, sends nothing and deletes its queue within a minute. The agent runs under launchd or systemd, so it never sees your shell's environment.

How opting out reaches running agents:

- `amicu telemetry disable` saves the choice, then right away stops every telemetry agent on this machine (from every project) and deletes every queue.
- Every `amicu apply`, including one with no changes to apply, checks consent first. If it resolves to off from any source (the file, `DO_NOT_TRACK=1` or `AMICU_TELEMETRY=0`), apply stops every telemetry agent on this machine and deletes every queue before doing anything else. If an agent cannot be stopped, apply fails and says so.
- When amicu stops a deployment for good (`destroy`, or removing it from the config), it also deletes that deployment's queue and its anonymous id.

If you opt in after deploying, a deployment gets its agent the next time `amicu apply` starts or updates it.

Not covered yet: Modal deployments get no agent, because the container does not carry the amicu binary. Windows deployments do not get one yet either.

### What is sent

Each upload is a JSON batch (schema version 2) of reports. Each report covers one deployment over one 5-minute window. The exact format is published as a JSON Schema in the repository, at `crates/amicu-telemetry/schema/telemetry-batch.v2.schema.json`. The ingestion service rejects any field not listed here.

| Group | Fields |
|---|---|
| Batch | `schema_version`, `batch_id` (random, so a retried upload is stored once), `reports` |
| Identity | `install_id`: a random id for this installation, generated once and stored in `~/.local/share/amicu/telemetry/identity.json`. `deployment_id`: a random id per deployment. Neither is derived from your machine, user or deployment name. |
| Window | `start_unix_s`, `duration_s` (300) |
| Software | `amicu_version`, `runtime.name` (`llama.cpp` or `vllm`), `runtime.version` |
| Model | `model.name` and `model.quantization`. `model.name` is the Hugging Face repo id only for models from well-known public publishers (for example `meta-llama`, `Qwen`, `mistralai`, `unsloth`, `bartowski`). Any other model, including local files, URLs and other repos, is sent as `custom`. |
| Configuration | `context_length`, `batch_size`, `provider` (one of `local`, `local_apple`, `local_cpu`, `on_prem`, `modal`, or `other` for anything else), `region`. `region` is only a cloud provider's region code. It is never sent for a deployment on your machine, and never derived from your location or locale. |
| Hardware | `accelerator` (model, for example `nvidia-geforce-rtx-4090`), `accelerator_count`, `vram_bytes` (per accelerator, rounded to whole GiB), `cpu_cores` (capped at 256), `memory_bytes` (rounded up to a power-of-two number of GiB, for example 24 GiB is sent as 32 GiB). The rounding keeps exact hardware sizes from identifying a machine. |
| Measurements | `requests` and `errors` (vLLM only), `prompt_tokens`, `output_tokens`, `output_tokens_per_s`, `decode_tokens_per_s`, the latency histograms `ttft_ms`, `e2e_ms` and `tpot_ms` (bucket counts and a sum, over fixed bucket bounds), `running_peak`, `waiting_peak`, `kv_cache_utilization_peak`, `preemptions`, `gpu_utilization`, `gpu_memory_peak_bytes` and `host_memory_peak_bytes` (both rounded to whole GiB) |

The payload has no field for prompts, completions or any request content, IP addresses, hostnames, file paths, endpoint URLs, usernames, or API keys and other secrets. Every text value must be a short token without spaces. A value that looks like an IP address or a credential is dropped before it is sent, and the server rejects it too.

Each upload is an HTTPS `POST` with `Content-Type: application/json`, `User-Agent: amicu/<version>` and an `Idempotency-Key` header set to the batch id. No credentials or tokens are sent. The ingestion service runs at `api.amicu.dev` and does not store the IP address a request comes from.

## Local files

Amicu writes `.amicu/` in your project, the service definitions described in [This machine](/docs/providers/local), and log files under `~/Library/Logs/amicu/` on macOS. With telemetry on, it also writes the telemetry identity and queue files under `~/.local/share/amicu/telemetry/`. Only the queued rollups are ever uploaded, and only while telemetry is on.

## The server crates

The repository also contains a separate server (`amicu-server`) backed by Postgres, used by the hosted product and for self-hosting. It is not part of the CLI workflow documented here.
