Day-2 operation has two halves, both owned by the Rust Management API. The API
**exposes measured metrics**; a Rust **recommendation engine** diagnoses
bottlenecks and returns advisory changes. The web app renders both and computes
neither (the thin-client rule — see the web RFC §4.4).

## Metric surface — `GET /stacks/:id/metrics`

The endpoint serializes a `StackMetrics` object for one stack over an
observation window. It is content-free by construction: every field is an
identifier, a count, or a measurement — never prompt or completion text.

Latency is reported as **distributions of percentiles (P50/P90/P99), never
means**. Utilizations and rates are fractions in `[0, 1]`.

```json
{
  "deployment": "chat_prod",
  "window_seconds": 60,
  "latency": {
    "ttft_ms": { "p50": 120, "p90": 480, "p99": 900 },
    "tpot_ms": { "p50": 14, "p90": 22, "p99": 35 },
    "e2e_ms":  { "p50": 900, "p90": 1800, "p99": 3200 }
  },
  "throughput": { "output_tokens_per_s": 850, "prompt_tokens_per_s": 4200, "requests_per_s": 6.1 },
  "concurrency": { "in_flight_requests": 24, "running_batch_size": 18, "max_num_seqs": 32, "seq_saturation": 0.56 },
  "queue": { "depth": 3, "wait_ms": { "p50": 5, "p90": 40, "p99": 120 }, "admitted": 3600, "rejected": 12 },
  "memory": { "kv_cache_utilization": 0.72, "preemptions": 0, "recomputations": 0, "oom_events": 0 },
  "gpu": { "sm_utilization": 0.68, "vram_used": "38GiB", "power_watts": 310 },
  "cost": { "per_hour": { "amount": 1.5, "currency": "USD" }, "per_million_tokens": { "amount": 0.42, "currency": "USD" }, "per_request": { "amount": 0.0006, "currency": "USD" }, "utilization_adjusted_per_hour": { "amount": 2.2, "currency": "USD" } },
  "reliability": { "error_rate": 0.001, "timeout_rate": 0.0, "restarts": 0 }
}
```

| Group | Fields |
|---|---|
| **Latency** | `ttft_ms`, `tpot_ms`, `e2e_ms` — each a P50/P90/P99 distribution |
| **Throughput** | `output_tokens_per_s`, `prompt_tokens_per_s`, `requests_per_s` |
| **Concurrency** | `in_flight_requests`, `running_batch_size`, `max_num_seqs`, `seq_saturation` |
| **Queue** | `depth`, `wait_ms` (distribution), `admitted`, `rejected` |
| **Memory / KV** | `kv_cache_utilization`, `preemptions`, `recomputations`, `oom_events` |
| **GPU** | `sm_utilization`, `vram_used`, `power_watts` |
| **Cost** | `per_hour`, `per_million_tokens`, `per_request`, `utilization_adjusted_per_hour` (idle burn) |
| **Reliability** | `error_rate`, `timeout_rate`, `restarts` |

## Recommendations

The engine takes the measured `StackMetrics` plus a `WorkloadEstimate` (the
expected behavior and the assumptions it was derived from — prompt/generation
length and concurrency), assigns a **bottleneck class**, and returns advisory
`Recommendation`s.

<Callout title="Advisory, never automatic">
  Recommendations are descriptive data. Nothing in the engine applies a change
  to a running stack — there is no apply path, and the `advisory` flag is always
  `true`. An operator decides.
</Callout>

Each recommendation is **explainable**. It carries:

- **Evidence** — the measured metrics that triggered it, each with its observed
  value, threshold, and direction (e.g. `gpu.sm_utilization` above `0.85`).
- **Rejected alternatives** — changes the engine considered and ruled out, with
  the reason (e.g. "downsize — GPU is already saturated").
- **Confidence and assumptions** — the estimate's stated assumptions plus any
  measured-vs-estimated **divergence** (e.g. "measured TTFT p90 900ms is 3.0x
  the estimated upper bound"), so a wrong call is attributable rather than
  presented as a point-estimate truth.

### Starter rules

| Bottleneck | Fires when | Suggests (advisory) |
|---|---|---|
| **Under-provisioned** | high queue wait + high GPU util + KV eviction | scale out / larger-VRAM GPU / raise KV cache |
| **Over-provisioned** | low GPU util while billing, no queueing | downsize / spot / fewer replicas |
| **Prefill-bound** | high TTFT, healthy TPOT | chunked prefill / cap prompt concurrency |
| **Decode-bound** | high TPOT | smaller/quantized model / better GPU / tensor-parallel |
| **Preemption / recompute** | vLLM preemptions or recomputations | raise `gpu-memory-utilization` / add VRAM headroom |

## Tier gating

Basic monitoring — reading the metric surface — is **Community**. The advisory,
performance-DB-backed recommendations are **Pro**. Each `Recommendation` carries
a `required_tier`, and a report can be filtered for the tier the caller holds; a
Community caller sees metrics but no recommendations.
