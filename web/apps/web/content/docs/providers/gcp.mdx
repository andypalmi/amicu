## Use this provider

```hcl
resource "hardware_profile" "gcp_t4" {
  provider = "gcp"
  region   = "europe-west4"
  accelerator {
    kind   = "gpu"
    model  = "t4"
    count  = 1
    memory = "16GiB"
  }
  memory = "15GiB"
  gcp {
    project          = "my-project-id"
    machine_type     = "n1-standard-4"
    provisioning     = "spot"
    max_run_duration = "2h"
    service_account  = "amicu-vm@my-project-id.iam.gserviceaccount.com"
  }
}
```

A complete example is in `examples/gcp-t4-spot`.

## Overview

`apply` creates one Compute Engine VM per deployment, with the GPU attached (N1) or built in (A2, A3, G2, G4), and one firewall rule for the serving port. A startup script runs the vLLM container behind amicu's key check: every route except `GET /health` needs the deployment's `api_key`. Only `runtime = "vllm"` is supported; llama.cpp is rejected (`AMICU-CAP-016`).

The VM boots the Deep Learning VM image `common-cu129-ubuntu-2204-nvidia-580`, which has the NVIDIA driver but not Docker. On first boot the startup script installs Docker Engine and the NVIDIA container toolkit from Docker's and NVIDIA's apt repositories, after checking each repository's signing key against a fingerprint built into amicu. This adds about one to two minutes before the vLLM image pull, so a small model is usually ready 6 to 10 minutes after `apply` creates the VM.

The startup script reports each boot as a guest attribute on the VM (`amicu/status`). If a step fails, for example the install, the image pull or the model load, `apply` stops waiting at once. It prints the failed step and the end of the script's log, then deletes the VM and firewall rule it created. Reading the report needs `compute.instances.getGuestAttributes`, which `roles/compute.instanceAdmin.v1` includes. Without that permission, `apply` waits for `/health` until its usual deadline.

The endpoint is `https://<VM IP>:8000`. The VM serves a self-signed certificate that amicu generates before it creates the VM. The certificate names no host you can resolve, so clients pin it instead of trusting a CA: `apply` writes it to `.amicu/state/<instance>.tls.crt` and prints its path and SHA-256 fingerprint. amicu pins it for its own health and exposure checks. A client that skips certificate verification is not protected. The firewall rule allows only the addresses in `allowed_source_cidrs`, or by default this machine's public IP as a `/32`. amicu never opens the port to `0.0.0.0/0` unless you list it.

The API key, the Hugging Face token and the TLS private key are stored in Secret Manager (one secret each, in the deployment's region only) before the VM is created. The VM's service account reads them at boot, so they are never in instance metadata. The secret ids and the certificate fingerprint are in the record `apply` writes to state first, so `destroy` removes the secrets even after a crash.

<Callout type="warning" title="Insecure metadata fallback">
  `insecure_metadata_secrets = true` skips Secret Manager and puts the three secrets in instance metadata, where anyone who can read the instance in the project can read them, and the console shows them. Use it only when Secret Manager cannot be used. TLS stays on.
</Callout>

The VM is deleted by Compute Engine after `max_run_duration` (default 8 hours) whatever else happens, and a preempted Spot VM is deleted too. `apply` writes the VM's record to state before it creates anything, tries the next zone of the region on a capacity stockout (at most 4 zones), and waits until vLLM answers. `amicu destroy` deletes the VM, then the firewall rule, then the secrets, confirms each is gone, and can be run again after a failure. It deletes only resources that carry amicu's owner marker (a label on the VM, a marker in the rule's description). A resource of the same name without it is left alone and reported.

## Setup and credentials

amicu uses Application Default Credentials: run `gcloud auth application-default login`, or set `GOOGLE_APPLICATION_CREDENTIALS`. To act as a service account, set `impersonate_service_account` in the block (or `GOOGLE_IMPERSONATE_SERVICE_ACCOUNT`). `apply` makes one read of the project before it writes anything, so missing credentials fail first. The caller needs permission to create and delete instances and firewall rules in the project, to create, version, set the IAM policy of and delete secrets (`roles/secretmanager.admin` covers it), and GPU quota in the region.

### The service account

The VM runs as a service account that reads its secrets. Create one once per project; it needs no project-level roles:

```sh
gcloud iam service-accounts create amicu-vm --project my-project-id
```

Set `service_account = "amicu-vm@my-project-id.iam.gserviceaccount.com"` in the `gcp {}` block. amicu itself grants `roles/secretmanager.secretAccessor` to that account on each of the deployment's secrets, one secret at a time, and never changes project-level IAM. The account that runs `apply` needs `roles/iam.serviceAccountUser` on the VM's service account, so it may attach it to a VM:

```sh
gcloud iam service-accounts add-iam-policy-binding \
  amicu-vm@my-project-id.iam.gserviceaccount.com \
  --member "user:you@example.com" --role roles/iam.serviceAccountUser
```

Without a `service_account` and without `insecure_metadata_secrets = true`, `validate`, `plan` and `apply` fail with `AMICU-CAP-016`.

| Variable | Needed for | Notes |
|---|---|---|
| `GOOGLE_APPLICATION_CREDENTIALS` (optional) | all commands | A service-account key file. Otherwise the `gcloud` login is used. |
| The deployment's `api_key` secret, for example `CHAT_API_KEY` | `apply`, and every client call | A random key (`openssl rand -hex 32`). It is stored in Secret Manager and read by the VM's service account at boot (instance metadata only with `insecure_metadata_secrets = true`). |
| `HF_TOKEN` (optional) | Gated Hugging Face repos | Delivered the same way, as its own secret. |
| `AMICU_GCP_VLLM_IMAGE` (optional) | Override the vLLM image | Process-wide. |

## Configuration reference

The `gcp {}` block on a `hardware_profile` with `provider = "gcp"`:

| Argument | Type | Default | Required | Notes |
|---|---|---|---|---|
| `project` | string | none | yes | Google Cloud project id (`AMICU-CAP-016` if missing). |
| `backend` | string | `compute` | no | `compute` (a VM) or `cloud_run` (a Cloud Run service, see [Cloud Run](#cloud-run)). |
| `zone` | string | first zone offering the GPU | no | Pins one zone. Otherwise the catalog zones of `region` that offer the GPU are tried in order. |
| `machine_type` | string | smallest catalog machine for the GPU | no | For N1 GPUs (T4, V100, P4) an `n1-standard-N`; the default is `n1-standard-4` per GPU. |
| `provisioning` | string | `spot` | no | `spot`, `flex_start` or `standard`. Not every machine offers every mode (`AMICU-CAP-018`, for example `standard` on `a3-highgpu-1g`). |
| `max_run_duration` | duration | `8h` | no | `10m` to `2880h` (120 days), or `168h` (7 days) with `flex_start`. Write it in `s`, `m` or `h`: days are not accepted. Compute Engine deletes the VM after it. |
| `idle_shutdown` | duration | off | no | Power the VM off after this long without a request (5m or more, shorter than `max_run_duration`). A watchdog on the VM polls vLLM's `/metrics`. After it fires the VM is only stopped, not deleted: its boot disk keeps billing and `max_run_duration` likely no longer applies, until the next `amicu apply` or `amicu destroy` deletes it. |
| `boot_disk_gb` | number | `100` | no | At least 50. |
| `service_account` | string | none | yes, unless `insecure_metadata_secrets` | Email of the account the VM runs as; it reads the VM's secrets from Secret Manager (`AMICU-CAP-016` if missing). |
| `insecure_metadata_secrets` | bool | `false` | no | INSECURE. Deliver the secrets as instance metadata instead of Secret Manager, readable by anyone who can read the instance. |
| `allowed_source_cidrs` | list | this machine's public IP `/32` | no | Who may reach the serving port. IPv4 only: an IPv6 CIDR is rejected (`AMICU-CAP-016`). |
| `impersonate_service_account` | string | none | no | Service account amicu acts as. |
| `access` | string | `public` | no | Cloud Run only: `public` (the API key is the only guard) or `iam` (callers also send a Google identity token). See [Cloud Run](#cloud-run). |

`region` is required unless `zone` is set, so the VM is placed where you expect. The profile's `region` and the project's `data_class` residency are checked against every candidate zone. A deployment on a VM runs one replica: `scaling {}` with more than 1 is rejected (`AMICU-CAP-016`).

Other checks: an unknown GPU or one not offered in the zone or region is `AMICU-CAP-017`.

## Cloud Run

With `backend = "cloud_run"`, `apply` creates one Cloud Run service per deployment instead of a VM. Each instance has one GPU: an L4 (at least 4 vCPU, 16 GiB) or an RTX PRO 6000 (at least 20 vCPU, 80 GiB). The profile's `memory` (and `cpu.cores`, when set) is used when it is above that minimum; below it is `AMICU-CAP-016`. The service scales to zero: while no instance runs, nothing is billed for compute. GPU instances are billed for as long as they run, from the moment a request starts one.

<Callout type="warning" title="Any request can start a billed instance">
  With the default `access = "public"`, Cloud Run does not filter requests, so any request to the URL, including an anonymous one or a plain `GET /health`, starts an instance when none is running. That instance is billed while it starts and loads the model (often minutes, the weights are downloaded again on each cold start) and until Cloud Run stops it after it has been idle for a while. The spend is capped by `max_replicas` instances at a time. Use `access = "iam"` to let only callers with a Google identity token reach the service.
</Callout>

```hcl
resource "hardware_profile" "gcp_cloudrun_l4" {
  provider = "gcp"
  region   = "europe-west4"
  accelerator {
    kind   = "gpu"
    model  = "l4"
    count  = 1
    memory = "24GiB"
  }
  memory = "16GiB"
  gcp {
    project         = "my-project-id"
    backend         = "cloud_run"
    service_account = "amicu-run@my-project-id.iam.gserviceaccount.com"
  }
}
```

A complete example is in `examples/gcp-cloudrun-l4`.

- **Endpoint and auth.** The endpoint is the service's `https://<service>-<hash>.<region>.run.app` URL, with Google-managed TLS. Every `/v1` route needs `Authorization: Bearer <api_key>`.
  - `access = "public"` (default): Cloud Run's IAM invoker check is turned off on this service only (no IAM policy is changed), and the API key is the only guard. After the deploy, `apply` checks that an anonymous request is refused and the key is accepted. An organization policy `constraints/run.managed.requireInvokerIam` forbids this; `apply` then names the policy and suggests `access = "iam"`.
  - `access = "iam"`: the IAM check stays on. Callers need `roles/run.invoker` on the service and send a Google identity token for the service URL in `X-Serverless-Authorization: Bearer <id token>`, plus the API key in `Authorization` (for example `curl -H "X-Serverless-Authorization: Bearer $(gcloud auth print-identity-token)" -H "Authorization: Bearer $CHAT_API_KEY" ...`). After the deploy, `apply` checks that an anonymous request is refused; it holds no identity token, so it does not send the key.

  If the check fails, `apply` deletes the service and secrets it created.
- **Secrets.** The API key (and `HF_TOKEN`, when set) are stored in Secret Manager in the service's region before the service is created. The service reads them as `service_account`, which amicu grants `roles/secretmanager.secretAccessor` on those secrets only.
- **Write-ahead record.** The service and secret names are written to state before anything is created. `destroy` deletes the service only if it carries amicu's owner label, waits until a read returns not found, then deletes the secrets. The record leaves state only after that.
- **Cold start.** The first request after an idle period starts an instance and loads the model. Cloud Run holds the request until the container is ready, which can take minutes, so give clients a long timeout. The startup probe on `/health` allows up to 30 minutes for the model download.
- **Scaling.** `scaling { max_replicas }` is the maximum number of instances (default 1). Each instance holds one GPU, so keep it within the region's Cloud Run GPU quota. `target_concurrency` is how many requests one instance serves at once (default 8). Zonal redundancy is off, which is cheaper and needs less quota.
- **Regions.** L4: `europe-west1`, `europe-west4`, `us-central1`, `us-east4`, `asia-southeast1` (`asia-south1` by invitation only). RTX PRO 6000: `europe-west4`, `us-central1`, `asia-southeast1`, `asia-south2`. Another region or GPU is `AMICU-CAP-017`.

Cloud Run cannot honour some settings, and `validate`, `plan` and `apply` reject them with `AMICU-CAP-019`: `zone`, `machine_type`, `provisioning`, `max_run_duration`, `idle_shutdown`, `boot_disk_gb`, `allowed_source_cidrs` and `insecure_metadata_secrets` in the `gcp {}` block, and `min_replicas` above 0 or `scaledown_window` in `scaling {}`. `access` is Cloud Run only. `accelerator.count` must be 1, and `service_account` and `region` are required (`AMICU-CAP-016`).

Before it writes anything, `apply` checks (read-only) that the Cloud Run Admin API and the Secret Manager API are enabled and that you may act as the `service_account`, and names the `gcloud` command or role that fixes each. The account that runs `apply` needs `roles/run.admin` (or permission to create, read and delete services), Secret Manager access as above, and `roles/iam.serviceAccountUser` on the service account. Create the service account as for a VM:

```sh
gcloud iam service-accounts create amicu-run --project my-project-id
```

## Operations

Before it writes anything, `apply` on a VM checks (read-only) that the credentials work, that the Secret Manager API is enabled, that the project has a `default` network (the firewall rule is attached to it) and that you may act as the `service_account`. Each failure names the fix, for example `gcloud services enable secretmanager.googleapis.com --project <project>` or granting `roles/iam.serviceAccountUser` on the service account. amicu never enables APIs or changes IAM itself.

`amicu plan` and `apply` compare state with Compute Engine and Cloud Run. A VM that is gone or stopped (a Spot preemption, the `max_run_duration` backstop, a delete outside amicu), or a Cloud Run service that is gone or whose revision failed, is reported as drift and marked pending: `apply` recreates it, `destroy` confirms what is left is removed. A service scaled to zero is not drift. `amicu orphans` lists VMs, firewall rules, Cloud Run services and Secret Manager secrets in the project that carry amicu's marker but that state does not record, with the `gcloud` command to delete each. It never deletes anything.

## Limits

- The certificate is self-signed and pinned, not CA-signed: clients must pin its fingerprint.
- vLLM only, one VM per deployment, no `env` block, no metrics or logs through amicu.
- Cloud Run: one GPU per instance, no minimum instances (always scales to zero), no CIDR allowlist, the idle timeout is Cloud Run's own, and with `access = "iam"` amicu cannot check that the API key is accepted.
- A4X (`a4x-*`, the GB200 and GB300 machines) is not supported yet: amicu has not been tested on its Arm (NVIDIA Grace) boot image and the arm64 vLLM container. `apply` and `plan` reject an `a4x-*` `machine_type`, and a GB200 or GB300 GPU never picks one by default.
- Prices in the catalog are illustrative values, not live quotes, so cost estimates are indicative.

## Troubleshooting

<Accordions>
  <Accordion title="apply says no Google Cloud credentials were found">
  Run `gcloud auth application-default login`, or set `GOOGLE_APPLICATION_CREDENTIALS` to a service-account key file. Nothing was created.
  </Accordion>
  <Accordion title="apply says no zone has capacity">
  Compute Engine had no GPUs of that kind in the zones tried. Retry later, pick another `region` or `zone`, another GPU, or `provisioning = "flex_start"`. What the run created was deleted.
  </Accordion>
  <Accordion title="apply says the startup script failed at a step">
  The VM reported that a boot step failed. The error names the step and shows the end of the script's log. `apply` deletes the VM and firewall rule it created, and the record stays in state until a later `apply` or `destroy` confirms they are gone. For the full boot log, run the `gcloud compute instances get-serial-port-output` command printed with the error while the VM still exists. If the error says the VM could not be deleted, it may still be billing: run `amicu destroy --target <deployment>`.
  </Accordion>
  <Accordion title="I cannot reach the endpoint">
  The firewall rule allows only `allowed_source_cidrs`, or the public IP of the machine that ran `apply`. If your address changed, set `allowed_source_cidrs` and run `apply` again.
  </Accordion>
  <Accordion title="apply or destroy refuses a secret">
  A Secret Manager secret of amicu's name exists without amicu's owner label, so amicu will not use or delete it. Rename or delete it yourself if it is not needed.
  </Accordion>
  <Accordion title="destroy says the Secret Manager API is not enabled, or a permission is missing">
  Enable the API (`gcloud services enable secretmanager.googleapis.com --project <project>`) or grant the account amicu runs as `secretmanager.secrets.get` and `secretmanager.secrets.delete` (`roles/secretmanager.admin`), then run `destroy` again. The record stays in state meanwhile. When no VM was ever created and the API is off, `destroy` treats the secrets as absent and releases the record.
  </Accordion>
  <Accordion title="destroy refuses a VM or firewall rule">
  It does not carry amicu's owner marker, so amicu will not touch it. Check it in the Google Cloud console; the record stays in state.
  </Accordion>
  <Accordion title="apply fails after I changed the project or the impersonated account">
  `apply` first tears down the old record, using the project and account that record names. If that project or service account is gone, the teardown fails on every `apply` until you revert the config to the old project and account (so `amicu destroy` can clean up), or, once you have checked in the Google Cloud console that nothing of amicu's is left, delete that deployment's record from `.amicu/state/state.json` by hand. No amicu command forgets a Google Cloud record.
  </Accordion>
  <Accordion title="validate or plan rejects the region">
  The region code must be one the catalog lists, and its jurisdiction must satisfy your [`data_class`](/docs/configuration/data-class) residency constraint. An unknown code is not guessed at: the residency check fails closed. See [Residency](/docs/concepts/residency).
  </Accordion>
</Accordions>
