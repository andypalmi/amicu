## Use this provider

```hcl
resource "hardware_profile" "gcp_t4" {
  provider = "gcp"
  region   = "europe-west4"
  accelerator {
    kind   = "gpu"
    model  = "t4"
    count  = 1
    memory = "16GiB"
  }
  memory = "15GiB"
  gcp {
    project          = "my-project-id"
    machine_type     = "n1-standard-4"
    provisioning     = "spot"
    max_run_duration = "2h"
    service_account  = "amicu-vm@my-project-id.iam.gserviceaccount.com"
  }
}
```

A complete example is in `examples/gcp-t4-spot`.

## Overview

`apply` creates one Compute Engine VM per deployment, with the GPU attached (N1) or built in (A2, A3, G2, G4), and one firewall rule for the serving port. A startup script runs the vLLM container behind amicu's key check: every route except `GET /health` needs the deployment's `api_key`. Only `runtime = "vllm"` is supported; llama.cpp is rejected (`AMICU-CAP-016`).

The endpoint is `https://<VM IP>:8000`. The VM serves a self-signed certificate that amicu generates before it creates the VM. The certificate names no host you can resolve, so clients pin it instead of trusting a CA: `apply` writes it to `.amicu/state/<instance>.tls.crt` and prints its path and SHA-256 fingerprint. amicu pins it for its own health and exposure checks. A client that skips certificate verification is not protected. The firewall rule allows only the addresses in `allowed_source_cidrs`, or by default this machine's public IP as a `/32`. amicu never opens the port to `0.0.0.0/0` unless you list it.

The API key, the Hugging Face token and the TLS private key are stored in Secret Manager (one secret each, in the deployment's region only) before the VM is created. The VM's service account reads them at boot, so they are never in instance metadata. The secret ids and the certificate fingerprint are in the record `apply` writes to state first, so `destroy` removes the secrets even after a crash.

<Callout type="warning" title="Insecure metadata fallback">
  `insecure_metadata_secrets = true` skips Secret Manager and puts the three secrets in instance metadata, where anyone who can read the instance in the project can read them, and the console shows them. Use it only when Secret Manager cannot be used. TLS stays on.
</Callout>

The VM is deleted by Compute Engine after `max_run_duration` (default 8 hours) whatever else happens, and a preempted Spot VM is deleted too. `apply` writes the VM's record to state before it creates anything, tries the next zone of the region on a capacity stockout (at most 4 zones), and waits until vLLM answers. `amicu destroy` deletes the VM, then the firewall rule, then the secrets, confirms each is gone, and can be run again after a failure. It deletes only resources that carry amicu's owner marker (a label on the VM, a marker in the rule's description). A resource of the same name without it is left alone and reported.

## Setup and credentials

amicu uses Application Default Credentials: run `gcloud auth application-default login`, or set `GOOGLE_APPLICATION_CREDENTIALS`. To act as a service account, set `impersonate_service_account` in the block (or `GOOGLE_IMPERSONATE_SERVICE_ACCOUNT`). `apply` makes one read of the project before it writes anything, so missing credentials fail first. The caller needs permission to create and delete instances and firewall rules in the project, to create, version, set the IAM policy of and delete secrets (`roles/secretmanager.admin` covers it), and GPU quota in the region.

### The service account

The VM runs as a service account that reads its secrets. Create one once per project; it needs no project-level roles:

```sh
gcloud iam service-accounts create amicu-vm --project my-project-id
```

Set `service_account = "amicu-vm@my-project-id.iam.gserviceaccount.com"` in the `gcp {}` block. amicu itself grants `roles/secretmanager.secretAccessor` to that account on each of the deployment's secrets, one secret at a time, and never changes project-level IAM. The account that runs `apply` needs `roles/iam.serviceAccountUser` on the VM's service account, so it may attach it to a VM:

```sh
gcloud iam service-accounts add-iam-policy-binding \
  amicu-vm@my-project-id.iam.gserviceaccount.com \
  --member "user:you@example.com" --role roles/iam.serviceAccountUser
```

Without a `service_account` and without `insecure_metadata_secrets = true`, `validate`, `plan` and `apply` fail with `AMICU-CAP-016`.

| Variable | Needed for | Notes |
|---|---|---|
| `GOOGLE_APPLICATION_CREDENTIALS` (optional) | all commands | A service-account key file. Otherwise the `gcloud` login is used. |
| The deployment's `api_key` secret, for example `CHAT_API_KEY` | `apply`, and every client call | A random key (`openssl rand -hex 32`). It is stored in Secret Manager and read by the VM's service account at boot (instance metadata only with `insecure_metadata_secrets = true`). |
| `HF_TOKEN` (optional) | Gated Hugging Face repos | Delivered the same way, as its own secret. |
| `AMICU_GCP_VLLM_IMAGE` (optional) | Override the vLLM image | Process-wide. |

## Configuration reference

The `gcp {}` block on a `hardware_profile` with `provider = "gcp"`:

| Argument | Type | Default | Required | Notes |
|---|---|---|---|---|
| `project` | string | none | yes | Google Cloud project id (`AMICU-CAP-016` if missing). |
| `backend` | string | `compute` | no | `compute`. `cloud_run` parses but `apply` cannot deploy it yet (`AMICU-CAP-019`). |
| `zone` | string | first zone offering the GPU | no | Pins one zone. Otherwise the catalog zones of `region` that offer the GPU are tried in order. |
| `machine_type` | string | smallest catalog machine for the GPU | no | For N1 GPUs (T4, V100, P4) an `n1-standard-N`; the default is `n1-standard-4` per GPU. |
| `provisioning` | string | `spot` | no | `spot`, `flex_start` or `standard`. Not every machine offers every mode (`AMICU-CAP-018`, for example `standard` on `a3-highgpu-1g`). |
| `max_run_duration` | duration | `8h` | no | `10m` to `2880h` (120 days), or `168h` (7 days) with `flex_start`. Write it in `s`, `m` or `h`: days are not accepted. Compute Engine deletes the VM after it. |
| `idle_shutdown` | duration | off | no | Power the VM off after this long without a request (5m or more, shorter than `max_run_duration`). A watchdog on the VM polls vLLM's `/metrics`. Compute Engine keeps a powered-off VM and its boot disk until the next `apply` or `destroy` deletes it. |
| `boot_disk_gb` | number | `100` | no | At least 50. |
| `service_account` | string | none | yes, unless `insecure_metadata_secrets` | Email of the account the VM runs as; it reads the VM's secrets from Secret Manager (`AMICU-CAP-016` if missing). |
| `insecure_metadata_secrets` | bool | `false` | no | INSECURE. Deliver the secrets as instance metadata instead of Secret Manager, readable by anyone who can read the instance. |
| `allowed_source_cidrs` | list | this machine's public IP `/32` | no | Who may reach the serving port. IPv4 only: an IPv6 CIDR is rejected (`AMICU-CAP-016`). |
| `impersonate_service_account` | string | none | no | Service account amicu acts as. |

`region` is required unless `zone` is set, so the VM is placed where you expect. The profile's `region` and the project's `data_class` residency are checked against every candidate zone. A deployment on this provider runs one replica: `scaling {}` with more than 1 is rejected (`AMICU-CAP-016`).

Other checks: an unknown GPU or one not offered in the zone or region is `AMICU-CAP-017`.

## Operations

Before it writes anything, `apply` checks (read-only) that the credentials work, that the Secret Manager API is enabled, that the project has a `default` network (the firewall rule is attached to it) and that you may act as the `service_account`. Each failure names the fix, for example `gcloud services enable secretmanager.googleapis.com --project <project>` or granting `roles/iam.serviceAccountUser` on the service account. amicu never enables APIs or changes IAM itself.

`amicu plan` and `apply` compare state with Compute Engine. A VM that is gone or stopped (a Spot preemption, the `max_run_duration` backstop, a delete outside amicu) is reported as drift and marked pending: `apply` recreates it, `destroy` confirms its firewall rule is removed. `amicu orphans` lists VMs, firewall rules and Secret Manager secrets in the project that carry amicu's marker but that state does not record, with the `gcloud` command to delete each. It never deletes anything.

## Limits

- The certificate is self-signed and pinned, not CA-signed: clients must pin its fingerprint.
- vLLM only, one VM per deployment, no `env` block, no metrics or logs through amicu.
- Cloud Run is not supported by `apply` yet.
- A4X (`a4x-*`, the GB200 and GB300 machines) is not supported yet: its Arm boot images ship without Docker and the NVIDIA container toolkit. `apply` and `plan` reject an `a4x-*` `machine_type`, and a GB200 or GB300 GPU never picks one by default.
- Prices in the catalog are illustrative values, not live quotes, so cost estimates are indicative.

## Troubleshooting

<Accordions>
  <Accordion title="apply says no Google Cloud credentials were found">
  Run `gcloud auth application-default login`, or set `GOOGLE_APPLICATION_CREDENTIALS` to a service-account key file. Nothing was created.
  </Accordion>
  <Accordion title="apply says no zone has capacity">
  Compute Engine had no GPUs of that kind in the zones tried. Retry later, pick another `region` or `zone`, another GPU, or `provisioning = "flex_start"`. What the run created was deleted.
  </Accordion>
  <Accordion title="I cannot reach the endpoint">
  The firewall rule allows only `allowed_source_cidrs`, or the public IP of the machine that ran `apply`. If your address changed, set `allowed_source_cidrs` and run `apply` again.
  </Accordion>
  <Accordion title="apply or destroy refuses a secret">
  A Secret Manager secret of amicu's name exists without amicu's owner label, so amicu will not use or delete it. Rename or delete it yourself if it is not needed.
  </Accordion>
  <Accordion title="destroy says the Secret Manager API is not enabled, or a permission is missing">
  Enable the API (`gcloud services enable secretmanager.googleapis.com --project <project>`) or grant the account amicu runs as `secretmanager.secrets.get` and `secretmanager.secrets.delete` (`roles/secretmanager.admin`), then run `destroy` again. The record stays in state meanwhile. When no VM was ever created and the API is off, `destroy` treats the secrets as absent and releases the record.
  </Accordion>
  <Accordion title="destroy refuses a VM or firewall rule">
  It does not carry amicu's owner marker, so amicu will not touch it. Check it in the Google Cloud console; the record stays in state.
  </Accordion>
  <Accordion title="apply fails after I changed the project or the impersonated account">
  `apply` first tears down the old record, using the project and account that record names. If that project or service account is gone, the teardown fails on every `apply` until you revert the config to the old project and account (so `amicu destroy` can clean up), or, once you have checked in the Google Cloud console that nothing of amicu's is left, delete that deployment's record from `.amicu/state/state.json` by hand. No amicu command forgets a Google Cloud record.
  </Accordion>
  <Accordion title="validate or plan rejects the region">
  The region code must be one the catalog lists, and its jurisdiction must satisfy your [`data_class`](/docs/configuration/data-class) residency constraint. An unknown code is not guessed at: the residency check fails closed. See [Residency](/docs/concepts/residency).
  </Accordion>
</Accordions>
