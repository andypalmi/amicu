## Use this provider

```hcl
resource "hardware_profile" "runpod_l4" {
  provider = "runpod"
  region   = "eu"
  accelerator {
    kind   = "gpu"
    model  = "l4-24gb"
    count  = 1
    memory = "24GiB"
  }
  memory = "32GiB"
}
```

RunPod is one of the providers `amicu apply` and `amicu destroy` can deploy to. New to RunPod? <RunPodSignupLink /> to create an account.

## Overview

A hardware profile with `provider = "runpod"` makes `apply` create a RunPod Serverless load-balancing endpoint. Both `vllm` and `llama_cpp` runtimes work, using the stock images. The model must come from Hugging Face; the worker downloads it.

The endpoint scales to zero when idle and is billed per second while workers run. `amicu destroy` deletes the endpoint and the RunPod secrets amicu created for it.

By default amicu keeps no warm workers and allows one worker (min 0, max 1). For more throughput, raise `max_replicas` in the deployment's [`scaling {}`](/docs/configuration/deployment) block. Other defaults: scale out at 32 in-flight requests per worker, scale a worker down after 900 s idle.

## Setup and credentials

Two kinds of key are involved. Keep them apart: RunPod's gateway checks the endpoint key on every request, and amicu will not accept your management key as an endpoint key.

| Variable | Needed for | Notes |
|---|---|---|
| `RUNPOD_API_KEY` | `plan`/`apply` refresh, `apply`, `destroy` | The management key. Create it in the RunPod console under Settings, API Keys, as a Restricted key with `api.runpod.io/graphql` set to Read/Write (needed for the REST API). Add `api.runpod.ai` access as you see fit. |
| The deployment's `api_key` secret, for example `CHAT_API_KEY` | `apply`, and every client call | A second RunPod API key, used as the endpoint key. See below. |
| `HF_TOKEN` (optional) | Gated or private Hugging Face repos | Stored as a RunPod secret and injected into the worker. |
| `AMICU_RUNPOD_VLLM_IMAGE`, `AMICU_RUNPOD_LLAMACPP_IMAGE` (optional) | Override the base image | Process-wide. There is no HCL field for the image. |

Export values in your shell. Never write them into HCL (see [Secrets](/docs/security/secrets)).

### The endpoint key

RunPod's gateway checks the key and strips the `Authorization` header before the request reaches the worker, so the runtime never sees it. That is why the deployment's `api_key` must be a RunPod API key with `api.runpod.ai` access. Create a second Restricted key in the console with:

- `api.runpod.io/graphql`: None
- `api.runpod.ai`: Read/Write, or restricted to the endpoint

Then export it as the deployment's secret:

```bash
export RUNPOD_API_KEY=...   # management key
export CHAT_API_KEY=...     # endpoint key
```

amicu refuses a deployment whose `api_key` is the management key. An `api_key` that RunPod's gateway rejects fails `apply` with the HTTP status. A runtime `--api-key` flag or `API_KEY` variable cannot be set on RunPod, because the runtime would reject every request.

## Example

```hcl
resource "model" "qwen" {
  source {
    registry  = "hugging_face"
    reference = "unsloth/Qwen3.5-9B-GGUF"
  }
  architecture   = "qwen3"
  modalities     = ["text"]
  artifact {
    format       = "gguf"
    quantization = "q6_k"
  }
  context_length = 32768
  variant {
    quantization = "q6_k"
    file         = "Qwen3.5-9B-UD-Q6_K_XL.gguf"
    size         = "8350MiB"
  }
}

resource "hardware_profile" "runpod_l4" {
  provider = "runpod"
  region   = "eu"
  accelerator {
    kind   = "gpu"
    model  = "l4-24gb"
    count  = 1
    memory = "24GiB"
  }
  memory = "32GiB"
}

resource "deployment" "chat" {
  model    = model.qwen.id
  hardware = hardware_profile.runpod_l4.id
  runtime  = "llama_cpp"
  api_key  = secret("CHAT_API_KEY")
  llama_cpp {
    context_length = 32768
    port           = 8080
    n_gpu_layers   = -1
  }
}
```

Run `amicu validate`, `amicu plan`, then `amicu apply`. `apply` waits for the endpoint's health check, which includes the first cold start and model download, and prints the endpoint URL. A `vllm` deployment works the same way: set `runtime = "vllm"` and a `vllm {}` block as in the [Modal example](/docs/providers/modal#example-vllm).

## Calling the endpoint

The endpoint URL has the form `https://<endpoint id>.api.runpod.ai`. Send the endpoint key as a bearer token, with a capital `B`:

```bash
curl "$URL/v1/chat/completions" \
  -H "Authorization: Bearer $CHAT_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model": "unsloth/Qwen3.5-9B-GGUF", "messages": [{"role": "user", "content": "Hello"}]}'
```

With the OpenAI Python SDK, `api_key=os.environ["CHAT_API_KEY"]` and `base_url=f"{url}/v1"` are enough; the SDK sends `Authorization: Bearer`. There are no extra gateway headers.

## Configuration reference

| Argument | Type | Default | Required | Notes |
|---|---|---|---|---|
| `provider` | string | none | yes | `"runpod"`. |
| `region` | string | none | no | `eu`, `us`, `ca`, `apac`, or an exact data center id from [Regions](#regions). Unset lets RunPod place workers anywhere. |
| `accelerator.kind` | string | none | yes | Must be `gpu`. |
| `accelerator.model` | string | none | yes | A GPU id from [GPUs](#gpus), or a name that resolves to exactly one of them (see [GPU names](/docs/configuration/hardware-profile#gpu-names)). |
| `accelerator.count` | number | none | yes | GPUs per worker. |
| `accelerator.memory` | size | none | yes | VRAM, for the fit check. |
| `memory` | size | none | yes | Host RAM. |
| deployment `api_key` | `secret(...)` | none | yes | A RunPod API key with `api.runpod.ai` access. |

## GPUs

Use an exact catalog id such as `l4-24gb` or `h100-sxm-80gb`. A short name such as `l4` works only when, together with `accelerator.memory`, it names exactly one card. Ambiguous names (`h100`, `a100`) and unknown ids fail `amicu validate` with `AMICU-CAP-012` or `AMICU-CAP-013`.

amicu places the deployment in the card's RunPod GPU group and excludes the group's other cards, so only the card you named is used.:

| Group | Cards (ids) | VRAM |
|---|---|---|
| 16 GB | `rtx-a4000-16gb`, `rtx-a4500-20gb`, `rtx-4000-ada-20gb`, `rtx-2000-ada-16gb` | 16 to 20 GB |
| 24 GB | `l4-24gb`, `rtx-a5000-24gb`, `rtx-3090-24gb` | 24 GB |
| 24 GB (Ada) | `rtx-4090-24gb` | 24 GB |
| 32 GB | `rtx-5090-32gb` | 32 GB |
| 48 GB | `a40-48gb`, `rtx-a6000-48gb`, `l40-48gb`, `l40s-48gb`, `rtx-6000-ada-48gb` | 48 GB |
| 80 GB | `a100-sxm4-80gb`, `a100-pcie-80gb`, `h100-sxm-80gb`, `h100-pcie-80gb`, `h100-nvl-94gb` | 80 to 94 GB |
| 141 GB | `h200-sxm-141gb` | 141 GB |
| 96 GB | `rtx-pro-6000-96gb`, `rtx-pro-6000-maxq-96gb`, `rtx-pro-6000-server-96gb` | 96 GB |
| 180 GB and 288 GB | `b200-180gb`, `b300-288gb` | 180 and 288 GB |

Some cards, such as the MI300X and the H200 NVL, are only offered as pods, not on Serverless. They need a Pods mode that amicu does not have yet; it is coming.

## Regions

`region = "eu"` restricts placement to RunPod's EU data centers: EU-RO, EU-SE, EU-NL and EU-CZ, plus Iceland (EUR-IS) and Norway (EUR-NO). The other groups are `us`, `ca` and `apac`. An exact data center id (case-insensitive) pins one site. A region outside the residency your [`data_class`](/docs/configuration/data-class) requires is rejected, and an unknown region is an error, not "anywhere". See [Residency](/docs/concepts/residency).

| Data center | Location | Group |
|---|---|---|
| `EU-RO-1` | Romania | `eu` |
| `EU-SE-1` | Sweden | `eu` |
| `EU-NL-1` | Netherlands | `eu` |
| `EU-CZ-1` | Czechia | `eu` |
| `EUR-IS-1` | Iceland | `eu` |
| `EUR-NO-1` | Norway | `eu` |
| `US-CA-1` | California | `us` |
| `US-GA-1` | Georgia | `us` |
| `US-KS-2` | Kansas | `us` |
| `CA-MTL-1` | Montreal | `ca` |
| `AP-JP-1` | Japan | `apac` |
| `OC-AU-1` | Australia | `apac` |

## Costs

Only running workers are billed, per second; idle and initializing workers are free. With no traffic, nothing runs and nothing is billed. The 24 GB group (L4, RTX A5000, RTX 3090) is about $0.69 per hour per worker; see the [RunPod price list](https://www.runpod.io/pricing) for current rates, which vary by GPU and change over time. `amicu plan` shows indicative estimates from amicu's bundled catalog, not live quotes.

To keep spend bounded, remember the defaults: one worker at most, none kept warm. Run `amicu destroy` when you are done.

## Limits

- A single request is capped at about 5.5 minutes. Keep generations short enough to finish inside it.
- Cold starts take time: a new worker pulls the image and downloads the model onto its disk, so the first request after idle is slow, and a `503` or a wait is normal.
- Logs are available only from live workers. A scaled-to-zero endpoint has none to read; use the RunPod console while a worker is up.
- Only GPU accelerators are valid.
- The model must come from Hugging Face.
- Flags that refer to local files and secret-bearing flags are rejected before any RunPod call.
- Pods mode is not available yet.

## Troubleshooting

<Accordions>
  <Accordion title="RunPod needs RUNPOD_API_KEY set">
    Export the management key (`RUNPOD_API_KEY`) with `api.runpod.io/graphql` Read/Write, then run again. Nothing was changed.
  </Accordion>
  <Accordion title="RunPod deployments need an api_key">
    Add `api_key = secret("NAME")` to the deployment and export `NAME` as a RunPod API key with `api.runpod.ai` access. The runtime has no key of its own on RunPod.
  </Accordion>
  <Accordion title="amicu refuses the api_key">
    The `api_key` equals `RUNPOD_API_KEY`. Create a separate Restricted key for the endpoint (`api.runpod.io/graphql` None, `api.runpod.ai` Read/Write).
  </Accordion>
  <Accordion title="401 or 403 from the endpoint, or from the readiness check">
    The key lacks `api.runpod.ai` access to this endpoint, or the client sent it wrongly. Use `Authorization: Bearer <key>` with a capital `B`.
  </Accordion>
  <Accordion title="The endpoint did not become ready in time">
    The worker may still be pulling the image or downloading the model, or no GPU of that type was free in your region. Check the worker logs in the RunPod console, try a wider `region` or another card, and run `apply` again.
  </Accordion>
  <Accordion title="A 503 or a slow first response">
    A worker is cold-starting. Retry after a moment. With no warm workers, expect this after every idle period.
  </Accordion>
  <Accordion title="AMICU-CAP-012 or AMICU-CAP-013">
    The GPU name is ambiguous or not in the catalog. Use an exact id from [GPUs](#gpus).
  </Accordion>
  <Accordion title="The deployment lives in another RunPod account">
    `RUNPOD_API_KEY` belongs to a different account than the one that created the endpoint. Switch to a key of that account. Nothing was changed.
  </Accordion>
  <Accordion title="validate or plan rejects the region">
    The region must be a group or data center id from [Regions](#regions), and its jurisdiction must satisfy your [`data_class`](/docs/configuration/data-class) residency constraint.
  </Accordion>
</Accordions>
