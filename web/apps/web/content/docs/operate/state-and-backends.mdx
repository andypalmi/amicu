For what state contains and why it is safe to keep, see [Security: State](/docs/security/state). This page covers operating it.

## Location

The CLI stores state in the project directory:

| Path | Content |
|---|---|
| `.amicu/state/state.json` | The applied resource graph, the started endpoints, the `pending` deployments and the stop records (below) |
| `.amicu/state/state.json.bak` | The previous version of `state.json`, copied on save only when the current file is valid |
| `.amicu/state/state.lock` | The lock file |
| `.amicu/config.yaml` | Project config. `init` writes `state.backend: local`. |

`local` is the only state backend the CLI implements. There is no remote state backend for the CLI yet.

Treat `state.json` as sensitive operational data. Do not edit it by hand. `amicu init` adds `.amicu/` to `.gitignore`. Do not share state through version control: the lock is local to one machine, so two people applying from a committed `state.json` can overwrite each other and orphan running resources. A state serial with compare-and-swap saves is planned (amicu-planning#218).

## Locking

`apply`, `destroy` and `amicu modal stop` take an advisory lock on `.amicu/state/state.lock` for their whole read, refresh, plan, apply, and save sequence. The lock belongs to the operating system process: when the process dies, the kernel releases it, so there is no stale lock to clean up.

If another amicu process holds the lock, the command fails with a message naming the holder (pid, command, start time). To wait instead, pass a timeout:

```bash
amicu apply --lock-timeout 60
```

## State v2 fields

Current state files are version `v2`. Besides the graph and endpoints, they hold two fields that make teardown possible without the config or the provider's dashboard:

- **`pending`**: deployments whose start was begun but not confirmed. Amicu writes them before the provider starts anything. `plan` treats them as absent, so `apply` recreates them, and `destroy` tries to confirm their stop.
- **`stops`**: one stop record per instance that may be running. Each record carries what is needed to stop it from state alone: the backend (`launchd`, `systemd` or `modal`), the identity (launchd label, systemd unit or Modal app name), and the provider's id once known. Host records also keep the uid and, for launchd, the domain (`gui/<uid>` or `user/<uid>`). Modal records keep the workspace and environment. A record is removed only after its stop is confirmed.

Amicu refuses to act on a record when the current machine or account does not match it. Each refusal names the mismatch and says how to fix it: switch `MODAL_TOKEN_ID` and `MODAL_TOKEN_SECRET` to the recorded Modal workspace, or re-run as the user that started the host instance. Nothing is changed in that case.

State written by v1 amicu has no `pending` or `stops`. The stop records are derived from the graph on load, and a v1 Modal app is stamped with a workspace only after amicu proves the app is in the active one. An older amicu that saves a v2 file drops these fields, so do not run an older build on a project after a v2 apply.

## Partial apply and destroy

If an apply or destroy fails after starting or stopping some deployments, those changes are recorded in state and the error lists them. Fix the cause and re-run the same command: deployments that already succeeded show no change and the command finishes the rest. See [Security: State](/docs/security/state) and [Plan, apply and state](/docs/concepts/plan-apply-state#destroy).

## Known limitations

- **Modal app name collisions.** Amicu names a Modal app `amicu-` plus the deployment id, lowercased, with separators such as `_` and `.` replaced by `-`. Two deployment ids that differ only in case or separator (for example `support_chat` and `Support-Chat`) map to the same app name. Amicu does not reject this yet, so do not give two deployments such ids. Name-based lookups can then find the wrong app.

## Drift

State can fall out of date if something changes a deployment outside amicu.

- **Remote providers (Modal today).** Before each `plan`, `apply` and `destroy`, amicu asks Modal which recorded apps still exist. A deployment whose app is not found by name is kept in state as `pending`, and a `drift:` line is printed (to stderr with `--output json`). `plan` then shows a `create`, `apply` recreates the app, and `destroy` tries to confirm the stop by app id or, if none is recorded, by name. If the lookup fails, amicu prints a `warning: could not check Modal for live apps` and uses state as is.
- **Local services.** There is no automatic refresh. If you stopped a service by hand, remove the deployment from the configuration and apply, or stop and re-add it. See [Troubleshooting](/docs/troubleshooting).

## Starting over

If `state.json` is corrupt or missing but `state.json.bak` is valid, amicu refuses to continue and names the backup. Inspect it, and if it is correct restore it with `cp .amicu/state/state.json.bak .amicu/state/state.json`. If state is lost or corrupt with no usable backup, `plan` shows `create` for everything. Stop the running services first (see [This machine](/docs/providers/local) and your [provider's page](/docs/providers)), then delete `state.json` and `state.json.bak` and apply. Only do this with explicit intent: amicu forgets what it started.
