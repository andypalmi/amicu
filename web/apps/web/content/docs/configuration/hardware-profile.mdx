---
title: hardware_profile
description: Declare where a deployment runs.
---

A `hardware_profile` names the provider, optional region, and the compute a deployment runs on. Capacity checks compare the model against its memory.

## Examples

Apple Silicon, local:

```hcl
resource "hardware_profile" "dev_mac" {
  provider = "local_apple"
  accelerator {
    kind   = "apple_silicon"
    model  = "m4_pro"
    count  = 1
    memory = "48GiB"
  }
  memory = "48GiB"
}
```

CPU only, local:

```hcl
resource "hardware_profile" "cpu_box" {
  provider = "local_cpu"
  cpu {
    model = "ryzen_9_7950x"
    cores = 16
  }
  memory = "64GiB"
}
```

A remote GPU provider (Modal here), one L4 GPU in the EU:

```hcl
resource "hardware_profile" "gpu_l4" {
  provider = "modal"
  region   = "eu-west"
  accelerator {
    kind   = "gpu"
    model  = "l4"
    count  = 1
    memory = "24GiB"
  }
  memory = "32GiB"
}
```

## Fields

| Field | Type | Required | Description |
|---|---|---|---|
| `provider` | string | yes | `local`, `local_apple`, `local_cpu`, `on_prem`, `modal`, or a preview/planned provider id (see [Providers](/docs/providers)) |
| `region` | string | no | Provider region code. Used for residency checks. |
| `accelerator` | block | no | GPU, TPU, or Apple Silicon |
| `accelerator.kind` | string | yes | `gpu`, `tpu`, `apple_silicon`, or `cpu` |
| `accelerator.model` | string | yes | For a GPU, a [GPU id](#gpu-names) such as `h100-sxm-80gb` or a short name that resolves to one (`l4`). For Apple Silicon, the chip: `m4_pro`, `m5_max`, `m3_ultra` (any shipped chip, `m1` to `m5` base/Pro/Max/Ultra; chip only, the memory size goes in `memory`) |
| `accelerator.count` | number | yes | Number of accelerators |
| `accelerator.memory` | size | yes, except for a GPU id | Memory of one accelerator (VRAM or unified memory). For a GPU it must match the card's VRAM; when `model` is a GPU id it can be left out and defaults to the card's VRAM. |
| `accelerator.bandwidth_gbps` | number | no | Memory bandwidth in GB/s. Recorded for planning; not read by the fit check yet. |
| `cpu` | block | no | Host CPU |
| `cpu.model` | string | yes | CPU model name |
| `cpu.cores` | number | yes | Core count |
| `memory` | size | yes | Host RAM |
| `interconnect` | string | no | `nvlink`, `pcie`, `infiniband`, or `ethernet` |
| `price` | block | no | Price block with a `per_hour` money block |

```hcl
resource "hardware_profile" "priced" {
  provider = "modal"
  accelerator {
    kind   = "gpu"
    model  = "h100-sxm-80gb"
    count  = 1
  }
  memory = "64GiB"
  price {
    per_hour {
      amount   = 3.95
      currency = "USD"
    }
  }
}
```

## Providers

Local providers (`local`, `local_apple`, `local_cpu`, `on_prem`) run on this machine and bind to loopback. Every other provider serves the endpoint off-machine, so its deployments must set `api_key`. See [Providers](/docs/providers).

How `accelerator`, `memory`, and `cpu` map to a provider's request is provider-specific. For example, on Modal `h100-sxm-80gb` with `count = 2` becomes `H100:2`. See the [provider page](/docs/providers).

## GPU names

Every GPU amicu knows is one exact card with a canonical id of the form `<family>[-<variant>]-<vram>gb`, in lowercase with hyphens:

- `family` is the product name: `a100`, `h100`, `l40s`, `rtx-4090`, `rtx-pro-6000`.
- `variant` appears only when a family ships in more than one form factor or edition: `sxm` or `sxm4` (NVIDIA's own spelling for that generation), `pcie`, `nvl`, `maxq`, `server`, `mig`.
- `vram` is the card's nominal memory in GB, always present.

`accelerator.model` resolves to exactly one card, using `accelerator.memory` when it is needed:

- A canonical id names one card. If `memory` is set it must be within 2% of the card's VRAM, read as GB or GiB: `80GiB`, `80GB` and `nvidia-smi`'s 81559 MiB all match an 80 GB card; `96GiB` does not match `h100-nvl-94gb`.
- An exact provider spelling such as RunPod's `NVIDIA A100-SXM4-80GB` or `nvidia-smi`'s `NVIDIA H100 80GB HBM3` names one card regardless of `memory`.
- A family (`h100`), a family and variant (`a100-sxm4`), or a family and size (`a100-80gb`) works only when `memory` leaves a single card (the nearest size wins). `h100` with `94GiB` is `h100-nvl-94gb`, and `l4` is always `l4-24gb`.
- Anything else is `AMICU-CAP-012`. On `modal` and `runpod`, which place GPUs by catalog card, it is an error, so a bare ambiguous name (`h100`, `a100`) now needs an exact id there; elsewhere it is a warning. The message lists the candidates:

```text
  error [AMICU-CAP-012] hardware_profile `gpu`: `a100` with 80GiB is ambiguous: a100-sxm4-80gb (80 GB), a100-pcie-80gb (80 GB); set `accelerator.model` to one of these ids
```

Matching ignores case and punctuation and drops the words `NVIDIA`, `GeForce`, `Tesla`, `AMD`, and `Radeon`. A GPU the catalog does not know is `AMICU-CAP-013`: an error on `modal` and `runpod`, which place GPUs by catalog id, and a warning elsewhere. `amicu plan` shows the resolved card, for example `gpu.h100-sxm-80gb (80 GB)`. Rewriting a name to the card it already ran as (`h100` with `80GiB` on RunPod or Modal was the SXM part) is not a change and does not restart the deployment.
