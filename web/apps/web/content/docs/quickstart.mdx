## 1. Choose where to run

Two equal paths. Pick one; steps 2 and 3 are shared.

| | [Path A: on this machine](#path-a-on-this-machine) | [Path B: on a GPU provider](#path-b-on-a-gpu-provider) |
|---|---|---|
| Where | macOS or Linux, launchd or systemd user service | A remote GPU provider you have an account with |
| Runtime | llama.cpp or vLLM | llama.cpp or vLLM |
| Endpoint | Loopback, `api_key` optional | Public, `api_key` required |
| Status | Supported | Today `apply` supports Modal; Hetzner, OVHcloud, Scaleway, RunPod and SSH are in preview, and AWS, Azure, GCP and Nebius are planned |

See [Providers](/docs/providers) for every provider and its status.

## 2. Install

amicu runs on macOS and Linux (arm64 and x86_64). Windows is not supported.

```bash
curl -LsSf https://amicu.dev/install.sh | sh
```

The installer downloads a prebuilt binary and puts `amicu` in `~/.local/bin`. It edits your shell profile, so open a new shell, then check it:

```bash
amicu --version
amicu --help
```

With Homebrew:

```bash
brew install andypalmi/tap/amicu
```

To build from source instead, you need Rust 1.97 or newer:

```bash
cargo install --locked --git https://github.com/andypalmi/amicu amicu-cli   # installs into ~/.cargo/bin
```

Or clone and build:

```bash
git clone https://github.com/andypalmi/amicu.git
cd amicu
cargo build --release -p amicu-cli
export PATH="$PWD/target/release:$PATH"
amicu --help
```

## 3. Initialize a project

Create an empty directory and run `init` in it.

```bash
mkdir my-stack && cd my-stack
amicu init --example
```

`init` creates `amicu.hcl` (only a comment header, no resources), `variables.amicu.hcl` (a placeholder), and `.amicu/` (project config and state). It never overwrites existing files.

For a working starter, add `--example`. A bare `--example` picks the one for this machine: macOS gets `mac`, Linux with `nvidia-smi` gets `linux-cuda`, and any other Linux gets `linux-cpu`. Its hardware profile is the detected machine, and it picks a Qwen3 GGUF model and context length that fit its memory. It replaces the header-only `amicu.hcl` while that is unchanged, and never overwrites a file you edited. To choose yourself:

```bash
amicu init --example             # detect this machine
amicu init --example mac         # Apple Silicon, llama.cpp with Metal
amicu init --example linux-cuda  # NVIDIA GPU, llama.cpp with all layers on the GPU
amicu init --example linux-cpu   # no GPU, llama.cpp on the CPU
amicu init --example modal       # Modal serverless GPU (Path B)
```

A local example must match the machine it runs on. See [Init examples](/docs/reference/cli#init-examples). The same files are in the repository under [`examples/`](https://github.com/andypalmi/amicu/tree/main/examples). To see what fits before you pick, run `amicu catalog fits`.

## Path A: on this machine

Requirements:

- `llama-server` from llama.cpp on your `PATH` (on macOS, `brew install llama.cpp`). `apply` resolves it from `PATH` to an absolute path and fails with `llama-server not found on PATH; install with ...` if it is missing. `amicu doctor` reports whether it is found.
- A GGUF file for the model. Amicu does not download it; you do, once.

### The starter config

`amicu init --example` writes an `amicu.hcl` like this one. On a Mac with 48 GiB of memory it serves `Qwen/Qwen3-8B-GGUF` (`Qwen3-8B-Q4_K_M.gguf`, about 5 GB) with llama.cpp. Smaller machines get a smaller model, so the model id, file name and context length below depend on your machine:

```hcl
resource "model" "qwen3_8b" {
  source {
    registry  = "hugging_face"
    reference = "Qwen/Qwen3-8B-GGUF"
  }
  architecture   = "qwen3"
  modalities     = ["text"]
  artifact {
    format       = "gguf"
    quantization = "q4_k_m"
  }
  context_length = 32768
  variant {
    quantization = "q4_k_m"
    file         = "Qwen3-8B-Q4_K_M.gguf"
    size         = "5027783488B"
  }
}

resource "hardware_profile" "local_dev" {
  provider = "local_apple"
  accelerator {
    kind   = "apple_silicon"
    model  = "m4_pro"
    count  = 1
    memory = "48GiB"
  }
  memory = "48GiB"
}

resource "deployment" "qwen3_8b_local" {
  model    = model.qwen3_8b.id
  hardware = hardware_profile.local_dev.id
  runtime  = "llama_cpp"
  llama_cpp {
    context_length = 32768
    port           = 8000
    n_gpu_layers   = -1
  }
}
```

`variant.size` is an integer number of bytes; `"5027783488B"` and `"5027783488"` mean the same. The `hardware_profile` is what `init` detected, and the fit check uses it. Change it only if you plan for another machine; see [Hardware profile](/docs/configuration/hardware-profile). Lower `context_length` if memory is tight.

### Get the GGUF

If `init` picked a smaller model for your machine, use the model id and file name from your `amicu.hcl` in place of `qwen3_8b` and `Qwen3-8B-Q4_K_M.gguf` below. The model resource id decides where the file goes: `models/<model id>/<variant.file>` relative to the project directory. Here that is `models/qwen3_8b/Qwen3-8B-Q4_K_M.gguf`. You can instead set `variant.file` to an absolute path.

```bash
mkdir -p models/qwen3_8b
curl -L -o models/qwen3_8b/Qwen3-8B-Q4_K_M.gguf \
  https://huggingface.co/Qwen/Qwen3-8B-GGUF/resolve/main/Qwen3-8B-Q4_K_M.gguf
```

For gated or private repos, add `-H "Authorization: Bearer $HF_TOKEN"`.

### Validate, plan, apply

```bash
amicu doctor
amicu validate
amicu plan
amicu apply
```

`doctor` and `plan` compare a local hardware profile with this machine. If the profile declares more memory than the machine has, they print the warning `AMICU-MEM-003`. It is only a warning, because `plan` may run on another machine than the one you deploy to, such as CI. Fix the profile, or ignore it when that is the case.

`plan` prints the exact `llama-server` command, with the model path relative to the project, `models/qwen3_8b/Qwen3-8B-Q4_K_M.gguf`. The service runs with the absolute path. `apply` shows the plan, asks for approval, installs a user service (launchd on macOS, systemd on Linux), starts it, and waits up to 15 minutes for `/health` to answer. If the service exits during startup, apply fails within seconds. On any failure it stops the service and the error gives the log location. See [This machine](/docs/providers/local).

### Send a request

The deployment has no `api_key`, so no header is needed; the endpoint is bound to `127.0.0.1`.

```bash
curl http://127.0.0.1:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "Qwen/Qwen3-8B-GGUF", "messages": [{"role": "user", "content": "Hello"}]}'
```

If the request fails, check that the service is running and read its log: on macOS `~/Library/Logs/amicu/<label>.out.log` and `<label>.err.log`, on Linux `journalctl --user --unit=<label>`. The label is `io.amicu.llama.<project_id>.qwen3_8b_local`, where `project_id` is in `.amicu/state/state.json`. A missing or wrong GGUF path is the usual cause; confirm the file exists at `models/qwen3_8b/` in the project directory.

To require a key even locally, add `api_key = secret("LOCAL_API_KEY")` to the deployment and export `LOCAL_API_KEY` before `apply`, then send `Authorization: Bearer $LOCAL_API_KEY`.

## Path B: on a GPU provider

The steps are the same for any provider:

1. Pick a provider from the [registry](/docs/providers) and create an account there.
2. Export its credentials in your shell. Never write them into HCL.
3. Set `provider` (and optionally `region`) on the `hardware_profile`.
4. Give the deployment an endpoint key: `api_key = secret("CHAT_API_KEY")`, with `CHAT_API_KEY` exported. Every off-machine endpoint needs one.
5. Run `amicu validate`, `amicu plan`, `amicu apply`.

`plan` shows `api_key: ******` and never reads the key value (it only checks that the variable is set). `apply` starts the deployment and then checks that the endpoint rejects anonymous requests and accepts your key. The first deploy downloads the weights and can take several minutes.

Today, `apply` supports Modal as a remote GPU provider. Hetzner, OVHcloud, Scaleway, RunPod and SSH are in preview (adapter built, not wired into `apply`), and AWS, Azure, GCP and Nebius are planned. Selecting one of those fails at `apply` with a clear error before anything starts. Each provider page has its own setup and troubleshooting.

## 4. Tear down

```bash
amicu destroy
```

`destroy` lists every deployment recorded in state, asks `Destroy these deployments? [y/N]`, and then stops each one and removes it from state. To tear down only some of them, pass `--target <name>` (repeatable). Use `--auto-approve` (alias `--yes`) to skip the prompt.

A deployment leaves state only after its stop is confirmed. If a stop fails, the command exits with an error, the deployment stays in state, and you can re-run `amicu destroy`. On macOS and Linux, destroy also deletes the service file, which holds the endpoint API key. Add `--purge` to also delete the host log files of the destroyed deployments. Modal cache volumes are never deleted. See [Plan, apply and state](/docs/concepts/plan-apply-state#destroy).

You can also delete a `deployment` from your HCL and run `amicu apply`; the plan then shows a `destroy` action for it.

Some providers also have a direct stop command; see the provider page (for example [Modal](/docs/providers/modal#monitoring)).
